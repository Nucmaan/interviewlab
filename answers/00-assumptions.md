# 00 · Assumptions and decisions

The brief says a reasonable, clearly stated assumption will not be penalised. This file lists every assumption and decision made while building the answers and the POC, with the reason for each.

## A. Technology

| #   | Decision                                                                                                                                                                            | Reason                                                                                                                                                                                                                                                                                        |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1  | **TypeScript** everywhere (Next.js 16 App Router, Node.js 24), **PostgreSQL 17**, Prisma 7, Redis 8 + BullMQ 5.                                                                     | One language for UI, API, worker and tests. PostgreSQL has the window functions, BRIN indexes, partitioning and PL/pgSQL the SQL questions need.                                                                                                                                              |
| A2  | BullMQ **5.81** instead of 6.x; Vitest **4.1** instead of 5.0; TypeScript **6.0** instead of 7.0; ESLint **9** instead of 10.                                                       | The newer majors were released only weeks before this test (BullMQ 6 changed its Redis backend API, typescript-eslint does not support TS 7 yet, several ESLint plugins used by `eslint-config-next` do not support ESLint 10). For a financial system, mature versions are the safer choice. |
| A3  | Auth.js **v5 (next-auth 5.0.0-beta)**.                                                                                                                                              | v5 is the version built for the App Router and is what the Auth.js docs recommend for Next.js 15/16, even though it is still labelled beta.                                                                                                                                                   |
| A4  | UI mutations use **Next.js Server Actions**; machine-to-machine traffic (bank and mobile money callbacks, bulk upload, reports) uses **REST route handlers** documented in OpenAPI. | Server actions give the forms end-to-end type safety with less code. Both paths go through the same permission guard (`apps/web/src/lib/rbac.ts`) and the same service functions, so security rules are identical.                                                                            |
| A5  | An extra workspace package **`packages/platform`** holds the logger, Redis, queue definitions, cache and event helpers.                                                             | The web app and the worker both need them. `packages/core` must stay pure (no I/O), so infrastructure code cannot live there.                                                                                                                                                                 |
| A6  | shadcn/ui-**style** components are written in the repo (`apps/web/src/components/ui`) rather than generated by the shadcn CLI.                                                      | Same pattern (Tailwind + `cva` + `cn`), fewer dependencies, and every line is visible for review.                                                                                                                                                                                             |
| A7  | Seed data is generated with a small seeded random generator and word lists, not a faker library.                                                                                    | Same data on every run (repeatable demos and tests), and one fewer dependency. All names are random combinations; emails use the reserved `.test` domain.                                                                                                                                     |

## B. Money and currency

| #   | Assumption                                                                                                                                                                        | Reason                                                                                                                                            |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1  | The **base (reporting) currency is the Somali Shilling (SOS)**. Payments can be in **USD or SOS**.                                                                                | The brief says "USD and local currency". Tariff figures in the brief (50 / 75 / 110 per m³, 200 service charge) are realistic in SOS, not in USD. |
| B2  | Every payment stores `amount`, `currency`, the `exchange_rate` used and `amount_base` (SOS). All totals, reports, journals and penalties use `amount_base`.                       | You cannot add USD and SOS together. Storing the rate used makes each conversion explainable later, even after rates change.                      |
| B3  | Rates are fetched from the mock rates API (`GET /rates`) by the worker every 15 minutes and stored in `exchange_rate`. A payment uses the latest stored rate when it is received. | The brief says rates are dynamic and come from a separate API. Storing them means a slow rates API never blocks payment processing.               |
| B4  | All money arithmetic in TypeScript is done in **integer cents** (`packages/core/src/money.ts`); the database uses `NUMERIC(14,2)`.                                                | Floating point cannot represent 0.1 exactly. Cents are exact for our value range.                                                                 |
| B5  | Assessments and water bills are raised in SOS.                                                                                                                                    | Government charges are set in local currency; USD payments are converted.                                                                         |

| `payment.amount_base`, `payment.exchange_rate`, `payment.bill_id`                                                                                                       | Multi-currency totals (B2). Water payments pay a bill, not an assessment.                                                                                                                                                      |

| `assessment.amount_paid`, `assessment.penalty_amount`, `assessment.control_number`                                                                                      | Status tracking (OPEN / PART_PAID / PAID), the penalty question, and the unique payment reference per assessment.                                                                                                              |
| `penalty_history` with `UNIQUE(assessment_id, run_date)`                                                                                                                | Required by the penalty question; the unique key is part of the idempotency guarantee.                                                                                                                                         |
| `tariff`, `tariff_band`                                                                                                                                                 | "Tariff values must come from configuration, not hard-coded values." Bands store an upper limit (`up_to_m3`, NULL for the last band).                                                                                          |
| `meter_reading.reading_flag` (NORMAL / ROLLOVER / METER_REPLACEMENT), `meter_reading.consumption_m3`, `water_account.meter_digits`                                      | A lower reading is only accepted when flagged; the number of digits is needed for rollover; storing consumption makes estimates and abnormal-consumption checks cheap.                                                         |
| `exchange_rate`, `idempotency_key`, `rejected_payment`                                                                                                                  | Currency conversion; duplicate request protection; invalid rows kept separately for admin review.                                                                                                                              |
| `audit_log` (with `prev_hash`, `hash`)                                                                                                                                  | Tamper-evident audit trail.                                                                                                                                                                                                    |

The user table is called `app_user` because `user` is a reserved word in PostgreSQL.                                                                                        |
| `reversal`                                                                                                                                                              | Reversals need a request → approve workflow with segregation of duties (a CHECK constraint enforces requester ≠ approver).                                                                                                     |

| `notification`                                                                                                                                                          | Outbox of SMS and email messages sent through the mock gateway.                                                                                                                                                                |
| `billing_cycle`                                                                                                                                                         | One row per monthly billing run, with its exception report.                                                                                                                                                                    |
| `system_config`                                                                                                                                                         | Penalty rules, thresholds, collection bank GL and other settings the administrator can change without a deployment.                                                                                                            |

## D. Business rules

| #   | Assumption                                                                                                                                                                                                                                                                                                               | Reason                                                                                                                                                                                                                                                                                                                                       |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | Only payments with status **DONE** count as collections. REVERSED and FAILED payments are excluded from every total.                                                                                                                                                                                                     | A reversed payment was never really collected.                                                                                                                                                                                                                                                                                               |
| D2  | Timestamps are stored in **UTC**; the business day is the UTC date.                                                                                                                                                                                                                                                      | Keeps the SQL simple. A production system in East Africa (UTC+3) would store a business date column.                                                                                                                                                                                                                                         |
| D3  | The financial year start month is configurable (`financial_year_start_month`, default January). The SQL function takes it as a parameter. A financial year is labelled by the calendar year in which it starts.                                                                                                          | The brief says "a given financial year" without saying when it starts.                                                                                                                                                                                                                                                                       |
| D4  | **Penalty:** months 1–3 at 5% per month and month 4 onwards at 10% per month, of the **unpaid principal** (`amount_due - amount_paid`), **simple interest**, **full calendar months only** (same rule as PostgreSQL `age()`), capped at **100% of the original amount_due**.                                             | These are the brief's rules; the words "per month" and "unpaid amount" leave compounding and partial months open, so we chose the simplest defensible reading.                                                                                                                                                                               |
| D5  | The penalty job **recalculates the total and SETs it**, but never lowers a penalty already charged (`GREATEST(current, recalculated)`).                                                                                                                                                                                  | Recalculating from scratch is what makes the job idempotent. Without the GREATEST rule, paying the principal would make the recalculated penalty drop to zero and wipe out a penalty the payer still owes. Only an approved waiver (out of scope) should lower a penalty. A production system would accrue penalties month by month instead. |
| D6  | An assessment is PAID when `amount_paid >= amount_due + penalty_amount`.                                                                                                                                                                                                                                                 | The penalty is owed too.                                                                                                                                                                                                                                                                                                                     |
| D7  | Payments are applied to the assessment or bill named in the payment. For water, a customer pays the **latest bill**, whose `total_due` already includes arrears carried forward.                                                                                                                                         | Keeps allocation simple and matches how customers pay utility bills.                                                                                                                                                                                                                                                                         |
| D8  | **Arrears ageing** (top 10 query) uses first-in-first-out: payments settle the oldest charges first.                                                                                                                                                                                                                     | The usual utility rule; it also makes the query a single, explainable formula.                                                                                                                                                                                                                                                               |
| D9  | **Collection efficiency** = successful payments against the bills of a billing month ÷ that month's `amount_billed`. It can exceed 100% when customers pay off arrears. HELD and CANCELLED bills are excluded.                                                                                                           | Arrears are billed only once (in the month they arose), so paying them later shows up as > 100%.                                                                                                                                                                                                                                             |
| D10 | **Meter rollover** is `(10^digits − previous) + current` and is only accepted when the reading is flagged ROLLOVER. **Meter replacement** treats the new meter as starting from 0. Any other lower reading is rejected.                                                                                                  | Stops typing mistakes from under-billing customers.                                                                                                                                                                                                                                                                                          |
| D11 | **Estimated reading** = rounded average of the last 3 ACTUAL consumptions (estimates are never based on earlier estimates). No actual history → the account goes on the exception report instead of being guessed.                                                                                                       | Stops estimation errors from compounding.                                                                                                                                                                                                                                                                                                    |
| D12 | **Abnormal consumption** = more than 200% of the average of the last 3 months (threshold configurable). A meter that read zero for 3 months and now shows any usage is also flagged. Such bills are created with status HELD and are not sent until an officer releases them.                                            | Brief: "flag abnormal consumption ... before bills are released".                                                                                                                                                                                                                                                                            |
| D13 | Bills are issued on the 1st of the month after the billing month and are due 21 days after the billing month ends (configurable `bill_due_days`).                                                                                                                                                                        | The brief does not give due dates.                                                                                                                                                                                                                                                                                                           |
| D14 | **Control numbers** use the format `PREFIX-YYYY-NNNNNNN-C` with a Luhn check digit (AS = assessment, WB = water bill). The sequence comes from a PostgreSQL sequence.                                                                                                                                                    | Readable, sortable, unique, and the check digit catches typing errors at the payment channel.                                                                                                                                                                                                                                                |
| D15 | **Duplicate detection** normalises phone numbers (+252 / 00252 / leading 0), emails (case, spaces) and national IDs (spaces, dashes) before comparing. Matches are flagged, never blocked.                                                                                                                               | Families and small businesses legitimately share phones.                                                                                                                                                                                                                                                                                     |
| D16 | The **Revenue Supervisor inherits** all Revenue Officer permissions (role hierarchy). The other system roles have no parent.                                                                                                                                                                                             | Brief: "hierarchical role system". A supervisor must be able to do what an officer does.                                                                                                                                                                                                                                                     |
| D17 | **Segregation of duties:** the user who requested a reversal can never approve it — enforced in code and by a database CHECK constraint.                                                                                                                                                                                 | Brief example; the database rule holds even if the application is bypassed.                                                                                                                                                                                                                                                                  |
| D18 | **Password policy:** at least 12 characters with upper, lower, number and symbol, not containing the email name. **Lockout** for 15 minutes after 5 failed logins. 2FA (TOTP) is optional per user.                                                                                                                      | Common government / NIST-aligned baseline.                                                                                                                                                                                                                                                                                                   |
| D19 | **Channel callbacks** are authenticated with HMAC-SHA256 over `timestamp + "." + rawBody` using a shared secret per environment; requests older than 5 minutes are rejected.                                                                                                                                             | Brief asks for signature verification; the timestamp stops replays. One shared secret for all mock channels in the POC; production would use one secret per channel.                                                                                                                                                                         |
| D20 | An `Idempotency-Key` replay with the **same body** returns the stored original response; the same key with a **different body** is rejected with HTTP 422. Keys are kept for 7 days.                                                                                                                                     | Standard idempotency-key semantics (as used by payment APIs).                                                                                                                                                                                                                                                                                |
| D21 | Exchange-rate precision: 6 decimal places. Converted amounts are rounded half-up to the cent.                                                                                                                                                                                                                            | Enough precision for USD/SOS.                                                                                                                                                                                                                                                                                                                |
| D22 | **FMIS** journals are built per business day: one credit line per payment (to the revenue type's GL code) and one debit line to the collection bank GL (`1101-000`, configurable). The payload sent to FMIS is summarised per GL code. Late payments for a day that was already posted go into a new batch for that day. | Full traceability in IRCUB, compact payload for FMIS.                                                                                                                                                                                                                                                                                        |
| D23 | On first start the worker posts **every unposted business day** to the mock FMIS (backfill of the seeded history). After that it posts the previous day at 01:00 every night; supervisors can post or retry any day manually.                                                                                            | Makes FMIS reconciliation meaningful for the seeded history.                                                                                                                                                                                                                                                                                 |
| D24 | Mock services keep their state in memory plus a JSON file on a Docker volume.                                                                                                                                                                                                                                            | They are simulations; persistence only needs to survive a restart.                                                                                                                                                                                                                                                                           |

## E. Scope decisions

| #   | Decision                                                                                                                                                                                                   | Reason                                                                                                                                                                                                  |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E1  | The monthly range-partitioning DDL is provided on a separate demo table (`payment_partitioned_example`) and is **not** applied to the Prisma-managed `payment` table.                                      | Prisma does not manage partitioned tables well, and a partitioned table cannot have `UNIQUE(external_ref)` without the partition key. The file explains how production would handle this.               |
| E2  | Raw SQL objects (functions, extra indexes) live in `/sql` and are applied by `packages/db/scripts/apply-sql.ts` after `prisma migrate deploy`. They are idempotent (`CREATE OR REPLACE`, `IF NOT EXISTS`). | One copy of each SQL answer, used both as the written answer and by the running system. New Prisma migrations should be authored with `prisma migrate diff` so these objects are not reported as drift. |
| E3  | The Taxpayer/Customer portal "payment" initiates a **mock mobile money** payment; there is no real payment page.                                                                                           | External systems must be simulated.                                                                                                                                                                     |
| E4  | SMS and email go to a mock gateway that records messages (viewable at `GET /messages` on the mock services).                                                                                               | No real messages may be sent.                                                                                                                                                                           |
| E5  | Penalty **waivers**, refunds of overpayments and partial reversals are out of scope.                                                                                                                       | Not requested; noted as future work.                                                                                                                                                                    |
| E6  | The Part 3 compliance module is designed (requirements, data model, flows) but **not built**.                                                                                                              | Part 3 is a written design exercise.                                                                                                                                                                    |
